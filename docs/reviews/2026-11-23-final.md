## High

### H1. A crafted slug in the URL deletes or probes any `.json` file (path traversal)
- Evidence: `api/companies.ts:143-145` (GET), `:164-175` (DELETE), `:177-197` (verify) use
  `req.params.slug` without `SlugSchema`. `recipes/store.ts:50-52` builds the path with
  `path.join(recipesDir, slug + ".json")`, and `:124-126` calls `rmSync`. Express 5 decodes `%2F` inside
  params, so `DELETE /api/companies/..%2Fprofile` (Content-Type `application/json`) deletes
  `server/data/profile.json`, and `..%2F..%2Fpackage` deletes `server/package.json`.
  `companyHasUserData` is false for these paths, so nothing blocks the delete. GET shows whether a file
  exists (404 vs 409). PUT and dry-run verify are safe only because they compare the URL slug with the
  slug in the zod-validated body.
- The H1 check below bypasses the Host check (`local-only.ts`) through M1.
- Fix: `router.param("slug", …)` → `parseOrThrow(SlugSchema, value)` (400). In `recipePath`, also
  assert that `path.dirname(path.resolve(...)) === path.resolve(recipesDir)`. Add tests for `..%2F`.

### H2. India classification marks foreign jobs as India (37 rows in the real DB)
Default views are India-only, so these jobs appear as India roles. Probed with the real profile
(`parseLocation`) and checked against `jobs.sqlite`:
- **"NCR" alias of Delhi NCR**: the Philippines' Metro Manila is also "NCR". 37 open Sutherland jobs
  ("Taguig, NCR, Philippines", "Mandaluyong City, NCR, Philippines", …) are stored with `is_india = 1`
  (Sutherland is not India-filtered). All are tier none today, but any CX-AI role in Manila would show
  up as an India high.
- **Overlap between "anywhere" and "Work from anywhere"**: `remoteTerms` contains "Work from anywhere"
  and `remoteRegionTerms` contains "Anywhere". `lib/location.ts:15-22` checks both on the same tokens,
  so `"Work from anywhere, United States"` and `"Remote - Anywhere in the US"` give `isIndia: true`.
  Talkdesk, Observe.AI and Verint (US-heavy boards, not India-filtered) have remote US roles at medium
  and high.
- **A city match ignores an explicit foreign country**: `"Hyderabad, Pakistan"`, `"Delhi, NY, USA"`,
  `"Kochi, Japan"`, `"Goa, Philippines"` and `"Remote (Asia - Japan)"` all give `isIndia: true`.
- Fix (deterministic, in `parseLocation` + profile):
  - Add a `foreignCountryTerms` list (Philippines, Pakistan, USA/United States, Japan, Singapore, …).
    When the string names one of them and no India term, India is decided only by an India term or by
    `indiaFiltered`.
  - Remove "NCR" as a bare alias (keep "Delhi NCR").
  - Check region terms on the tokens left after removing the matched remote phrase.
  - Add golden `loc-*` cases for each of the strings above before changing anything (golden-set rule).

### H3. A run can end without `run-finished`, so the UI stays on "Refreshing…" with the button disabled
- **Server**: `refresh/service.ts:154-157` marks the run `aborted` and rethrows, but never publishes
  `run-finished` (line 160 is skipped). The SSE route (`api/refresh.ts:69-77`) only ends the stream on
  `run-finished`. A typo in a hand-edited `profile.json` (`compileProfile(loadProfile())`, line 148)
  is enough to trigger this.
- **Web**: `web/src/api/events.ts:56-58` closes the stream when a snapshot shows an already finished
  run, but does not call `notifyFinished()`. After a sleep or Wi-Fi drop during a run, the reconnect
  snapshot says "finished", `refreshAfterRun` never runs, and the cached `latestRun` stays `running`
  (`refresh-controller.ts:35`; `refetchOnWindowFocus` is off in `main.tsx:10`). `events.ts:45-46`
  handles a permanently closed stream the same way, and `RefreshPanel.tsx:206` shows nothing for
  `closed`.
- Fix:
  - Publish `run-finished` with the aborted summary in a `finally`.
  - Call `notifyFinished()` on a snapshot whose run is not `running`.
  - Invalidate `LATEST_RUN_KEY` when the stream closes.
  - Show "Connection lost – reload" when the stream is `closed` while the run is still `running`.

## Medium

### M1. The Vite dev proxy lets any localhost page use the write API (CSRF via localhost)
- Evidence: `web/vite.config.ts:13-16` does not set `cors: false`. Vite 8's default CORS allows any
  `http://localhost:<port>` / `*.localhost` origin, and that middleware runs before the proxy. The proxy
  keeps `Host: localhost:5174`, so `requireLocalHost` passes, and nothing checks `Origin`.
- Result: any other local dev server, or a page served on localhost, can call POST/PUT/DELETE and read
  the replies. Together with H1, it can delete files.
- Fix: set `server.cors: false`. In `local-only.ts`, reject a request whose `Origin` header is present
  and is not `http://localhost|127.0.0.1|[::1]:5174|3001`.

### M2. Jobs are closed on incomplete data (old M1 + M2, plus a new case)
- **Mixed page cap and known-ids stop** (new): `adapters/paginate.ts:61` reports `page-cap` when any
  keyword hit the cap, even if other keywords stopped early on known IDs. `service.ts:358-366` then
  applies the 14-day close to all unseen jobs. Jobs on the later pages of the early-stopped keywords
  are never re-read in incremental runs, so they close after 14 days and reopen on a full run. This
  affects the three verified recipes that are newest-first and use keywords: `freshworks`, `google`
  and `wns` (`google` already stopped on `known-ids` in run 4). It is latent until a keyword hits the
  cap.
- **Unreadable rows get closed** (old M2): `service.ts:252` fails a company only when *all* rows are
  invalid, and `:356-367` closes everything not seen, including the rows that were dropped as
  unreadable.
- **A missing total ends paging early** (old M1): `oracle-hcm.ts:138` uses `TotalJobsCount ?? 0`.
  `successfactors.ts:8,68` assumes 25 rows per page (Foundever serves 10). `generic.ts:81` turns
  `Number(null)` / `Number("")` into 0. Each case ends paging after page 1, reports `complete: true`,
  and closes the rest of the board.
- Fix:
  - Have `paginate` return `stoppedEarlyOnKnownIds`, and apply the stale close only when it is false.
  - Skip closing when `jobsInvalid > 0` (and add a message).
  - Treat a missing or non-positive total as unknown, and keep paging while pages are full.
  - Add a test for each case.

### M3. One company's error outside its try/catch aborts the run while the others keep running (old L3)
- Evidence: `lib/concurrency.ts:17` uses `Promise.all`. `service.ts:173/205` (`events.publish`, whose
  listeners run synchronously), `:189` and `:197-200` (DB writes on the skipped/failure paths) are
  outside the per-company try.
- Result: the run is marked `aborted`, `activeRunId` is cleared (`:134`) while 3 workers keep writing,
  a second run or a profile save can start, `runningCompanies` keeps the dead slug, and H3 follows.
  The likely trigger is `SQLITE_BUSY` when a CLI run happens at the same time (M4).
- Fix: `Promise.allSettled` (or try/catch/finally around all of `refreshCompany`, with the delete and
  publish in `finally`). Make the fallback write best-effort.

### M4. CLI refresh/verify and the server run with no coordination
- Evidence: `cli/refresh.ts:43` calls `abortRunningRuns`, which marks the server's live run aborted.
  The one-run guard is only in memory (`service.ts:121`). Each CLI has its own HTTP client
  (`cli/refresh.ts:46`, `cli/verify-company.ts:40`), so the per-host limit becomes 2 req/s, which
  breaks the AGENTS.md rule. `jobsNew` is also counted twice.
- Fix: start a run inside an IMMEDIATE transaction that refuses if a run is `running`, and record
  pid + heartbeat on `refresh_runs`. `abortRunningRuns` should abort only runs whose process is gone.

### M5. A budget timeout or a late page error throws away everything already fetched (old M3)
- Evidence: `paginate.ts:36` throws on abort, and `service.ts:191-196` records `failed` and stores
  nothing. The tests assert this behaviour (`paginate.test.ts:171`). The sleeps at `http.ts:88` and
  `:150` ignore the signal. Freshworks and WNS share `api.smartrecruiters.com` (up to 30 listing pages
  + 20 detail requests each).
- Fix: catch the abort and errors after page 1 in `paginate`, and return
  `{complete:false, stopReason:"budget"|"error"}` so the jobs already read are stored and nothing is
  closed. Pass the signal to `sleep`.

### M6. CSV export is not built
- `GET /api/export.csv` is required by STEPS Step 8 and specified in ARCHITECTURE §7 "CSV export"
  (RFC 4180, every field quoted, BOM, formula-injection prefix), but it does not exist. There is no
  `lib/csv.ts`, no route and no UI button (only a comment in `types.ts:594`). CSV quoting therefore
  could not be reviewed, and Step 12 (README: "exporting CSV") is blocked.
- Fix: build it as specified, reusing the `/api/jobs` query without paging, with tests for quotes,
  CR/LF inside fields, `=+-@` prefixes, and the BOM.

### M7. Verify can mark an edited, untested recipe `verified`
- Evidence: `refresh/verify.ts:115-126` loads the recipe, waits up to 60 s for the network, then
  `writeVerification` (`recipes/store.ts:132-155`) merges the result into whatever file is on disk at
  that moment. If a PUT changes `fetch.url` during verify (which resets the recipe to `unverified`),
  the old result stamps `verified` + `verifiedOn` onto the new, untested fetch. This breaks the
  AGENTS.md accuracy rule. If the company was deleted during verify, the result is a 500 (ENOENT).
- Fix: compare `ats/fetch/fieldMap/filters/status` on disk with the recipe that was verified; if they
  changed, skip the write and return 409. A missing file gives 404.

### M8. Tokens in a URL or body can be saved into recipe files in the repo
- Evidence: the recipe schema (`types.ts:71, 149-160, 250-256`) checks only header *names*.
  `parse-curl.ts:296-301` only warns about `?token=` / `?session=` / `user:pass@` URLs and body keys
  like `csrfToken`, and Save then writes them into `server/data/companies/<slug>.json`. This goes
  against the AGENTS.md rule "never store … session tokens".
- Fix: reject these in the schema's `superRefine` (URL userinfo; query or body keys matching an
  anchored secret-name pattern), so Save returns 400.

### M9. UI: errors and undo get lost
- `JobsPage.tsx:75-97` passes `onSuccess`/`onError` to `mutate` on one shared mutation. In TanStack
  Query v5 these callbacks fire only for the latest call, so after two quick status clicks the first
  one gets no Undo toast and no error toast. The Undo call itself has no `onError`. The rollback in
  `hooks.ts:111-112` restores the whole page snapshot and wipes the other optimistic change. Fix: use
  `mutateAsync` per call, and roll back only the affected job.
- `AddCompanyDialog.tsx:173-183`: if the create succeeds and the verify after it fails, the dialog
  says "slug already exists", and every retry POSTs again (409). Fix: remember that the create
  succeeded and on retry only verify.
- `ProfilePage.tsx:58-60` calls `setDraft(null)` on success, which drops edits typed during the save
  (the editors stay enabled). `JobsPage.tsx:100`: the notes drawer falls back to the copy of the job
  taken when it opened once the job leaves the page, so it shows the old status and notes, and Undo
  uses the wrong previous status. `JobsPage.tsx:169` shows "No jobs match" on a page past the end
  (`total > 0`).

### M10. Network cost: failed or empty description requests are repeated every run
- Evidence: `service.ts:317-325` re-selects a job whenever its stored snippet is empty, so a detail
  page that keeps failing (`successfactors.ts:86`) or keeps returning `""`
  (`smartrecruiters.ts:124-126`) is fetched again on every run. The same first 20 rows always use the
  20-request budget, so other matching jobs never get a description.
- Fix: store `description_checked_at`, skip a job for N days after a failure or empty result, and
  put jobs that were never tried first.

## Checked and fine

- **No runtime LLM**: no AI SDK or LLM call in `server/src`, `web/src` or any `package.json`; scoring is
  keyword and weight based only.
- **Secrets**: none in recipes, fixtures, docs or `.opencode/`. The cURL fixtures use fake values. No
  recipe has headers other than `content-type`. `jobs.sqlite*` and `.env` are git-ignored, and nothing
  is committed yet.
- **Outgoing requests**: cookies are never sent (`credentials: "omit"`, Cookie stripped); import-curl
  keeps only the `accept`, `accept-language` and `content-type` headers and makes no network call.
- **Recipes** (87: 33 verified, 54 needs-manual): every verified recipe has `verifiedOn`; every
  needs-manual recipe has `manualSearchUrl` + `notes`; no company-specific `if` in the code; no
  LinkedIn, Naukri, Indeed, Glassdoor or Instahyre fetches (links only).
- **Adapter tests**: all 11 adapters are tested against saved real responses (sources in `SOURCES.md`).
- **Server binding and guards**: the server listens on `127.0.0.1`; the Host check ignores
  `X-Forwarded-Host`; every write needs JSON (blocks cross-site form or `text/plain` posts); there are
  no CORS headers on `:3001`.
- **SQL**: ORDER BY comes from a zod-enum map, LIKE input is escaped, and all values are bound
  parameters.
- **Profile save**: validated in full, re-scored in one transaction with the file write, and refused
  during a run.
- **Company isolation**: an adapter or parse error fails only that company, and all of a company's
  writes are in one transaction.
- **Job counting**: baseline runs count no new jobs; reopened jobs keep `first_seen_at`; an empty
  complete fetch closes nothing; `known-ids` on its own closes nothing.
- **HTTP**: 15 s timeout, 2 retries on 0/429/5xx only, 1 req/s per host within one process (one
  client shared by refresh and verify).
- **XSS**: no `dangerouslySetInnerHTML`; descriptions are plain text; stored job URLs must be absolute
  http(s); external links use `noopener`.
- **Profile preview**: dry-run results are keyed by the profile content (an old reply cannot
  overwrite a newer one), and Save is blocked while a preview is pending or failed.
